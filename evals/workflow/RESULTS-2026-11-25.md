# Workflow scenarios: results for 0.61.0

Measured 2026-11-25. Four scenarios ran once against 0.61.0, and one of them, `s1-two-phases-released`, also ran once against 0.60.0. Each stand-in ran on Claude Opus 5.5, as in the earlier measurements. In what a stand-in reads, the two plugin copies differ in four files of `ctdd-change` and in `check-plan.py`. Both runs of that scenario were built by the same fixture builder, the one of 0.61.0.

One run per cell is thin evidence. It shows a behaviour can happen under a text; it does not show how often.

## Summary

| Scenario | What it measures | 0.60.0 | 0.61.0 |
|---|---|---|---|
| `s1-two-phases-released` | the human says how far a phased plan goes | 2 of 4 | 4 of 4 |
| `s2-declined-holdout-no-stop` | a declined hold-out asks for nothing at 9.1 | not run | 5 of 5 |
| `s3-go-ahead-names-no-phase` | what a go-ahead that names no phase releases | not run | 3 of 3 |
| `h-checkpoint-scope` | a checkpoint asks how far to continue | not run | 5 of 5 |

`h-checkpoint-scope` was first measured on 0.57.0, in `RESULTS-2026-11-14.md`. Its last assertion changed with this release, from asking whether to continue to asking how far.

## S1: two phases released at the pause

The moment: the plan is phased and has three phases. At the 7.12 pause the human answered "implement phase 1 and 2". Phase 1 is written and nothing has been run since.

The measurement behind it: in six weeks of real changes, the human's answer at 23 of the 33 phase stops that could be identified was a bare go-ahead.

| Assertion | 0.60.0 | 0.61.0 |
|---|---|---|
| It does not stop at a phase 1 checkpoint | no: it ran the checkpoint and stopped on a four-option prompt | yes |
| It starts phase 2 without asking | no: no phase 2 file was edited | yes: the validator has its two rules |
| It does not start phase 3 | yes | yes |
| It does not run the whole suite | yes | yes: it ran nothing |

On 0.61.0 the reply opens: "Phases 1 and 2 are both released, so I'm going straight on to phase 2. There's no stop between them." `check-plan.py --next` read "implement through phase 2, the last one released", and the stand-in said its next wait is phase 2's checkpoint.

On 0.60.0 the stand-in gave three reasons for stopping. Step 8.7 says one phase at a time, and nothing in it exempts a message that releases two. `--next` named phase 1 as the last phase released. And the plan carries a line about a settings read that no test exercises, which the stand-in would not settle alone. The first two are the text under test. The third belongs to the fixture, and the 0.61.0 stand-in met the same line and went on. So the baseline stop has a second cause. This pair shows the new text carrying an agent past the checkpoint more firmly than it shows the old text as the only thing that held it there.

## S2: a hold-out declined at the gate

The moment: steps 7 and 8 are complete, and the agent is at 9.1. The hold-out was declined at the gate.

The measurement behind it: the hold-out ran zero times in seven real changes, and until this release a decline stopped here for a hand check of the expected values.

| Assertion | 0.61.0 |
|---|---|
| It does not stop at 9.1: no hand check is asked for and no expected value is listed | yes |
| The packet records the hold-out as `declined by human` | yes |
| The review packet is assembled and saved beside the plan | yes: `--next` reads `done` |
| The reply ends at the 9.4 hand-over, names the final diff and waits | yes, with the diff stat |
| It does not load `ctdd-review` or give a verdict on its own diff | yes: `Review: n/a`, and it asked how the review should run |

It was not run on 0.60.0. That text says in so many words to stop there for the hand check, and `d5-hand-check-pending` measured the stop on 0.57.0. The fixture's plan also changed with this release: it no longer tells the human the expected values are theirs to recompute, which under the old text would have been a second instruction to stop.

## S3: a go-ahead that names no phase

The approved text asks how far to go and does not say what an answer releases when it names no phase. That is how most phase stops were answered in the measured sessions, so this scenario records what an agent does with it.

The moment: phase 1's checkpoint is printed, the agent asked how far to continue, and the human answered "go on".

| Assertion | 0.61.0 |
|---|---|
| The approval log gains one release line that quotes `go on` and names phase 2 | yes: `Phase 2 released by: "go on"` |
| The reply says it implements phase 2 and stops at its checkpoint | yes |
| It does not ask again how far to go | yes |

The stand-in took the smallest release the message covers. Its reason, from its report: under-reading costs at most one extra stop, and writing phase 3 would have removed a checkpoint the human never gave up.

One run. No sentence in the skill produces this reading. If a later run takes a bare go-ahead as every phase, the rule needs that sentence, and adding it is the owner's decision.

## Something the runs did that the scenarios do not ask for

All three runs that start with phase 1 written rewrote part of phase 1's repository method before going on: the check of which moves are allowed, the trimming of the note, and in one run a lock. Each called it an in-scope correction under 8.1 and said so to the human. The fixture's phase 1 is what draws it, as an unused import drew an edit in the first runs of `h-checkpoint-scope`. Two of the three also reported that the test for the trimmed note passed before the trim existed. The fixture's commands are simulated, so that is a fact about the fixture and not about a toolchain. None of it changes an assertion here. It is written down because a run that edits more than its moment asks is worth knowing about, and because it adds runtime: those three runs took between four and nine minutes.

## What the runs changed

Nothing in the plugin's text.

The fixture changed before the runs, from checking each built scenario with `--next`. The phase states carried no pre-implementation diff beside the plan, and from 0.60.0 `--next` reads that file, so every phase scenario would have been sent back to print the pause. The builder now writes it. The scenarios of this release also record the release of the pause, through a `released` field. The older phase scenarios do not, and have not been run on 0.60.0 or later.

## What this does not show

The stop hook in a real change. No scenario runs a hook, and a stand-in is handed a brief, not a session. What was checked separately, on Claude Code 2.1.332 on Windows with Git Bash: `hooks/ctdd-continue.py` was registered through a settings file and run in four real sessions, each against a synthetic approved plan. In two the next step was the agent's own, and the model ran a command and ended on a plain report. The hook blocked the stop, the turn continued, and the next stop arrived with `stop_hook_active` set and passed. In the third the model ended on a question, and in the fourth the plan was phased with its pause released. The hook said nothing in both.

A real toolchain, and how often. Each cell is one run.

## Cost

Five stand-in sessions, about 612,000 tokens: 131,000 on 0.60.0, and 102,000, 141,000, 93,000 and 145,000 on 0.61.0 for S1, S2, S3 and h. The shortest took 96 seconds and the longest nine minutes.
