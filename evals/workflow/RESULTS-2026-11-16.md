# Workflow scenarios: results for 0.60.0

Measured 2026-11-16. This release answers one finding: a session that had been resumed lost the `ctdd-change` skill at a compaction, and went on without it. Two kinds of measurement were made. Live runs of Claude Code itself show what the harness does and that the new hook reaches the model. One stand-in run was made with a new scenario, and it did not measure what it was built to measure.

## Live runs: what the harness re-attaches

Claude Code 2.1.325, print mode with streamed input so that several turns and `/compact` run in one process, on its smallest model, in throwaway directories with the plugin enabled. The transcript of each run was read for the `invoked_skills` attachment that follows a compaction.

| Run | What the session did | Re-attached at the compaction |
|---|---|---|
| 1 | invoked `ctdd-routing`, then `ctdd-tests`, then compacted, all in one process | both |
| 2 | invoked `ctdd-routing`; exited; resumed; invoked `ctdd-tests`; compacted | `ctdd-tests` only |
| 3 | invoked both; exited; resumed; invoked nothing; compacted | nothing |
| 4 | run 1's session, resumed after its compaction; invoked nothing; compacted again | both |
| 5 | the same session, resumed again; invoked `ctdd-review`; compacted | all three |

The rule these five fit: the harness re-attaches the skills invoked in the running process, and on a resume it restores that set from the last compaction's own attachment and from nothing else. A skill invoked before a resume, with no compaction between the two, is gone at the next compaction whether or not anything is invoked after the resume. Run 3 is what separates this from the first hypothesis, which had the later invocation doing the damage.

The budget the documentation gives for re-attached skills, 5,000 tokens each within 25,000, does not come into it: in run 2 the skill that was dropped is about 4,000 characters long.

What this does not show: an interactive session, a second CLI version, or a resume across an upgrade. The drops this explains were all in interactive sessions that had been resumed after an upgrade, and the rule fits them, but the upgrade was not tested and was not needed to reproduce the loss.

## Live run: the hook after a real compaction

A fixture repository at the scenario's state, with `hooks/ctdd-resume.py` registered for the `compact` source through a settings file, its command running the script by its full path. (The example registration this run used was replaced by `hooks/hooks.json` once the owner decided to ship the hook enabled; the run below that one used the shipped file.)

1. The session invoked `ctdd-change` and read the plan's approval log. It exited.
2. Resumed, it invoked `ctdd-tests`, and was compacted. The compaction re-attached `ctdd-tests` only: the finding, reproduced with the two skills it happened to.
3. Claude Code ran the hook: exit 0, 528 ms, 1,143 characters of output. Asked to quote any note in its context that begins `CTDD resume`, the model quoted it whole: the plan, the approved revision, the evidence line, `Next: 7.12`, and the instruction.
4. Told to do what the note says first, the model made one call: the `ctdd-change` skill with the argument `resume <the plan's path>`.
5. Compacted again, the session had both skills re-attached.

A second hook, registered beside the first for this run only, recorded what the transcript held when the hooks ran. The compaction's own boundary record and its list of re-attached skills were not in it yet: at the second compaction the newest list visible was the first compaction's. So a hook cannot tell whether a skill came back, and this one always says to invoke it.

What this does not show: the hook registered from the plugin's own `hooks/hooks.json`, where `${CLAUDE_PLUGIN_ROOT}` stands for the path written out here; Linux or macOS; a Windows machine without Git Bash.

## The stand-in scenario: one run, and what it did not measure

`r-compaction-drops-the-skill` puts the stand-in just after a compaction, at the point where red state has been verified in a phased plan. Its brief carries what the harness leaves in context then: a summary shaped like the real one, the `ctdd-tests` skill with arguments that name an older plan revision and a test count the plan no longer has, the latest messages, and, when the plugin under test has the hook, the hook's note. It is not told which skill the session was following.

One run was made, on 0.59.0, which has no hook.

| Assertion | 0.59.0 |
|---|---|
| Reads `ctdd-change` and `execution.md` before replying | yes, unprompted |
| The reply is the 7.12 pause with its content | not reached |
| The pre-red diff is saved and `## Intended change` appended | not reached |
| Stops with a Decision prompt | yes, but for another reason |
| No production file changes; the approval still verifies | yes |

The stand-in ran the invariant suite, as `check-redstate.py` says to before the pause, and one layering test failed: the fixture state had the two outcome types in the feature folder, a placement three other scenarios are built on. It stopped there with the finding and two candidate fixes. That is the workflow working, on a moment the scenario did not mean to build.

Two things follow, and neither is a result about the hook.

- **The fixture state was wrong for this scenario.** `red-done` now puts the two types in the Domain, as `phase1-clean` does. Checked by hand on the rebuilt repository: the build succeeds, the six new tests fail, the layering suite passes, the three pins pass, and `check-plan.py --next` names 7.12. No stand-in has been run on the corrected state.
- **The baseline did not show the finding.** The stand-in read `ctdd-change` and its execution reference without being told to. The agent in the source session did not: it carried on as though it still had the skill. A stand-in starts by reading a brief that says what its context holds, so it knows what it lacks, and the source session's agent did not know. This scenario may not be able to show the finding however its fixture is built.

No run was made with the hook. The owner's rule for these runs is one before and one after, and the one before did not reach the moment.

**Decided 2026-11-19:** the scenario stays, recorded as unable to show this finding. What it can still check is what an agent does after reading the hook's note, which is the open question about the resume clause. It is run only if the owner asks.

## Live run, 2026-11-19: the hook from the plugin's own registration

After the owner's decisions the hook ships in `hooks/hooks.json` for `compact|resume`, and `ctdd-change` has its resume clause. Claude Code 2.1.328, the same fixture repository, no settings file of the run's own: the hook came from the plugin.

1. The session invoked `ctdd-change` with `resume <the plan's path>` and read the approval log. It exited.
2. Resumed, Claude Code ran the hook for the `resume` source: exit 0, 436 ms, 1,182 characters. Asked to quote any note beginning `CTDD resume`, the model quoted it, written "on resume", naming 7.12 with `release recorded ✗` in its evidence line.
3. The session invoked `ctdd-tests` and was compacted. The compaction re-attached `ctdd-tests` only: the finding again, on a newer version.
4. Claude Code ran the hook for the `compact` source: exit 0, 344 ms, 1,149 characters, and the model quoted its first line.

What this does not show: the model in this run was told to quote the note, not to act on it, so it did not invoke `ctdd-change` again; the run of 2026-11-16 above is the one that showed that a re-invoked skill survives the next compaction.

## Cost

One stand-in session on Opus, about 100,000 tokens and 88 seconds. The live runs came to about twelve cents on the smallest model.
