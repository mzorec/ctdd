# Workflow scenarios: results for 0.58.0

Measured 2026-11-15. One scenario, `m-heavier-harness`, ran once against 0.57.0 and once against 0.58.0, each stand-in on Claude Opus 5.5 as in the earlier measurement. The two plugin copies differ in `check-plan.py` and its tests and in nothing else. The skills are byte-identical, so what differs between the runs comes from the checker.

One run per cell is thin evidence. It shows a behaviour can happen under a version; it does not show how often.

## The moment

The plan is written and step 5.4 is next. It puts the validator's test and the handler's test in `tests/Shop.Application.IntegrationTests`, which sits beside `tests/Shop.Application.UnitTests`. Neither test needs a database: one checks a field rule, and the other maps a repository's answer to a result. The repository's `.ctdd.json` names its layers and its two kinds of test project. Everything else a first gate asks of a plan is already there, so where those two tests sit is the only thing left to decide.

In the source session it was seven handler tests. The layer check matched them, because both projects carry the layer's name, and the human found it by reading project names.

| Assertion | 0.57.0 | 0.58.0 |
|---|---|---|
| The plan that reaches the gate passes `check-plan.py` | yes, at its first run | yes, at its second run |
| Neither test is left in the integration project without a reason | no: both went to the gate there | yes: both moved to the unit project, in their `path:` lines and in the file list |
| Any reason given is true of the test | none was given | none was needed; the reply says neither test needs a database, which is true |
| The gate presentation shows, for each test, the kind of project it sits in | no: the table gives a layer per test, and the paths are in `Tests by file` | yes: `Application · UnitTests` on both rows, and one line saying the four other tests have no lighter project beside theirs |
| Nothing but the plan file changed, and the reply stops for approval and recommends nothing | yes | yes |

Two of five held on 0.57.0 and five of five on 0.58.0.

On 0.57.0 the altitude table read `Application | Application` for both tests and the checker exited 0. The stand-in's reply says nothing about where they sit. The paths were on the page, in `Tests by file`, which is how the human in the source session found the same thing.

On 0.58.0 the first run exited 1 with `HEAVIER HARNESS, NO REASON`, naming both tests and the unit project beside them. The stand-in moved both, and its reply opens by saying so and why. The reply grew from 805 words to 826.

## What this does not show

No run wrote a `needs:` line. Both tests plainly need nothing from the heavier project, and the stand-in moved them. So the scenario shows the refusal reaching the agent and the move being made, and says nothing about how honest a reason is when one is given, or about a test whose need is arguable. The checker cannot judge a reason either: it prints the reason at the gate, and the human does.

## Something the after-run did that the scenario does not ask for

It also moved two outcome types in the plan, from the feature folder to beside the port that returns them, and cited the layering test that the plan's `invariants:` line names. The baseline stand-in had the same plan and the same line and left them. The fixture plants that placement on purpose: three other scenarios start from it. One run each cannot say whether being sent back into the plan by the refusal is what made the second stand-in look. It changes no assertion here, and it is written down because a run that edits more than its moment asks is worth knowing about.

## What the runs changed

Nothing in the plugin. Two rules were added to the checker after the runs, from reading the code and not from a run: a lone dash is not a reason, and a reason given in an approved plan cannot be deleted afterwards without the question being asked again. Neither run wrote a `needs:` line or had an approval, so neither could have met them.

## Cost

Two stand-in sessions, about 171,000 tokens: 79,000 on 0.57.0 and 92,000 on 0.58.0. The first took 50 seconds and the second 79.
