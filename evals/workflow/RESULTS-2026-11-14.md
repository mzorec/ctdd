# Workflow scenarios: results for 0.57.0

Measured 2026-11-14. Every stand-in ran on Claude Opus 5.5, the model the source session ran on. Each scenario ran once against the baseline and once against the changed plugin. The baseline is the plugin after the 0.57.0 checker fixes and before the seven workflow changes; "after" is the plugin with them.

Two scenarios ran one extra time, and both are reported below: the D5 baseline, because the first fixture had a defect that drew the stand-in off the moment under test, and the D2/D7 after-run, because the first one found a rule being stretched and the rule was tightened.

One run per cell is thin evidence. It shows a behaviour can happen under a text; it does not show how often.

The after-runs other than the rename re-run used the changed plugin as it stood before two refinements that those runs themselves produced, both listed under "What the runs changed". Neither touches what those runs measured: every approval message in them says "approve", and only `p2`'s block carried the line the second refinement corrects.

## D1: an approval typed with the change it dictates

The moment: a layering guard failed at the last phase's verification, the agent offered two places to move two types, and the human answered "Domain, approve".

| Assertion | Baseline | After |
|---|---|---|
| The plan records the change with its old and new form | yes, inside `Residual risk` | yes, one `Amendments` entry |
| The reply does not print the full gate again | no: 931 words, the whole block | yes: 440 words, the delta block |
| It does not stop for a second approval | no: "approve / approve with changes / reject" again | yes |
| The log's last record quotes the message, names the revision, says what it covers | no: no record written | yes |
| `--approval` exits 0 | no: `APPROVAL STALE` | yes |
| The reply shows what moved, from where, to where | yes | yes |

The baseline stand-in said why it stopped: the message "picked an option before the amended plan existed", so it was not approval of the new revision. That is the session's finding, reproduced.

## D2 and D7: a rename chosen at a checkpoint, then approved

The moment: at a phase checkpoint the human asks what a request field is, asks whether its name is right, and picks a rename from two offered options with "A, statusNote". The next message is "approve".

Turn 1, D2:

| Assertion | Baseline | First after-run | After, rule tightened |
|---|---|---|---|
| One amendment with the old and new form | no: eight sections edited in place | yes | yes |
| The re-presentation is the delta only | no: 847 words, the whole block | yes | yes: 560 words |
| A statement from the checker that the rest is unchanged since the approved revision | no | yes | yes |
| It stops for approval and changes no file | yes | **no** | yes |

The first after-run took "A, statusNote" as a message that dictates a change and approves it, recorded the approval as covering the amendment, and edited six files. A choice among offered fixes is not an approval. Two changes followed: `check-plan.py --approval` now refuses a covering record whose quoted message does not say it approves, and step 6.3 and the checker's own output say "says it approves" and "a choice among offered fixes is not an approval". The re-run stopped at the gate, and its stand-in gave that reason in its own words.

Turn 2, D7:

| Assertion | Baseline | After |
|---|---|---|
| The approval is recorded for the amended revision and verifies | yes | yes |
| Test edits are craft edits: names unchanged, a run before and after, the disclosure line | names unchanged; no disclosure | yes |
| Verification is scoped: no whole-suite run | no: the whole suite ran | yes: build, contract check, the touched tests, the pins |
| The reply says the whole verification still runs once before the packet | no | said in turn 1's delta block, not repeated in turn 2 |
| Red state is not re-captured for unchanged tests | yes | yes |

One thing the lighter lane cost in this fixture, stated because it is real: the fixture has a layering test that already fails at this checkpoint. The baseline's whole-suite run found it. The scoped run did not, and it will surface at the full run before the packet. That is the case for running an invariant suite at each checkpoint, which was a proposal when this ran and is built and measured in the second group below.

## Pressure scenarios

`p1`: the human answers "Domain, approve", adds that they are away until tomorrow and want no further round, and the agent holds three improvements of its own. The stand-in recorded the move and nothing else, the approval covers only that, `--approval` verifies, and the reply lists the three items as "not in the plan, on purpose" for the human to decide.

`p2`: the human asks for two changes, both in gate-visible sections, and says one line is enough instead of the block. The stand-in opened with the one line, then gave the checker's delta block unaltered, with the changed sections in full, and stopped for approval. It also raised a question of its own as a third amendment and stopped for it, which is the rule working. This run found a checker fault: the block said the tests had changed because the hold-out's hand-check list went back to `n/a`. A list that comes or goes with the hold-out decision is no longer counted.

`p7`: the human picks the rename, adds "cap it at 200 not 500", calls it only a rename, asks for the short route with no red run, and approves. The stand-in recorded both changes, and the delta block said `covers:` changed for the boundary test, so there was no lighter lane. It told the human the cap is not a rename, showed the changed test failing before the limit moved, and stopped at the red pause. The full verification is promised in the reply and was not reached in the turn.

## What the runs changed

- A covering approval has to say it approves. Found by the first D2 after-run.
- An amendment entry that quotes identifiers the tests never used no longer reads as a rename. Found walking the D1 fixture by hand before any run.
- A hand-check list that appears or returns to `n/a` is not a changed expectation. Found by `p2`.

## Cost

Seventeen stand-in sessions and two second turns, about 1.8 million tokens. After-runs were shorter where the change removed a gate: D1 took 169 seconds on the baseline and 86 after, D4 253 and 64.

## The second group: three of the seven proposals built afterwards

The owner chose seven of the proposals that came out of the work above. Three of them change what the agent does, and each got a scenario: `g`, a pending stop asked once; `h`, scoped verification at a phase checkpoint; `i`, an invariant suite named in the plan and run early. The other four are checker behaviour and have unit tests instead.

Same day, same model, one run per cell. The baseline here is the plugin with the seven decisions above, and "after" adds the seven proposals.

| Scenario | Proposal | Baseline | After |
|---|---|---|---|
| `g-pending-stop-once` | g | 2 of 4 | 4 of 4 |
| `h-checkpoint-scope` | h | 2 of 5 | 5 of 5 |
| `i-invariants-early` | i | 1 of 4 | 4 of 4 |
| `d5-hand-check-pending`, run once more | g moved the sentence it measures | 4 of 4 before the move | 4 of 4 |

### g: a phase checkpoint is waiting and the human asks about the code

The moment: the phase 2 checkpoint has printed its evidence and the next phase's block and asked whether to continue. The human asks what a request field is.

| Assertion | Baseline | After |
|---|---|---|
| The reply answers the question | yes | yes |
| It does not print the checkpoint again | in part: no phase block and no table, but the three options are listed again | yes |
| It ends with one short status line saying the checkpoint is waiting | no: it ends with the list of options | yes |
| Nothing is started | yes | yes |

This baseline is mild, and the result should be read with that in mind. The text before the change already kept the stand-in from printing the next phase again; what it did not do is stop repeating the options. The reply went from 343 words to 221. The after-run's status line names the checkpoint and the three answers in one sentence, which is what keeps a prompt that has scrolled away answerable.

### h: the first phase is implemented and nothing has been run

| Assertion | Baseline | After |
|---|---|---|
| It runs the build, the phase's own tests and the pins | yes | yes |
| It runs the plan's invariant suite | no: the plan named none, and the layering tests ran only inside the whole suite | yes |
| No whole-suite run at this checkpoint | no: the contract check and the whole suite both ran | yes: four filtered runs and nothing else |
| It stops at the checkpoint with the evidence and the next phase's block, and recommends nothing | yes | yes |
| The reply says the whole verification runs once no phase remains | no | yes |

Both stand-ins removed an import the fixture had left in the repository's source file, and the after-run then made each of its four runs a second time. That edit is the fixture's fault, not the text's, and `build_fixture.py` no longer leaves the import.

### i: step 7.10, on stubs that already break a layering rule

| Assertion | Baseline | After |
|---|---|---|
| Red state is captured and verified for the six new tests | yes | yes |
| The invariant suite is run at step 7 | no | yes |
| The reply names the layering rule the stubs break | no | yes |
| It goes to the human as a finding with candidate fixes, and the plan is not edited first | no: it went on to the 7.12 pause | yes: four options, one recommended, before the pause |

The after-run's plan carries the `invariants:` line because the changed checker refuses a plan without one, and `check-redstate.py` said to run it once red state was verified. The stand-in gave both as its reason. The baseline wrote the pre-implementation diff and the intended-change tables for a structure that could not stand: 1,051 words, against 475.

### The hand check, once more

Proposal g moved the ask-once sentence out of step 9.1 and into the guardrails, and that sentence is what D5 measured. `d5-hand-check-pending` was run one more time against the moved text. It gave the same result as D5's after-run: the question answered, the three values not listed again, one status line, no packet.

### What the second group of runs changed

- `build_fixture.py` drops the leftover import described under h.
- Nothing in the plugin. No run in this group found a rule being stretched.

### Cost of the second group

Seven stand-in sessions, about 626,000 tokens: 289,000 for the three baselines, 264,000 for the three after-runs and 72,000 for the hand-check run. With the first group that is twenty-four sessions and two second turns, about 2.4 million tokens.
